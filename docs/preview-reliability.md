# Preview reliability and Browser Steps

Browser visual previews share the existing global Chromium admission lease with scheduled captures. `CHROMIUM_CONCURRENCY` remains the hard process limit (default `1`): a waiting preview does not start a browser, reserve an extra slot, or change worker concurrency.

`PREVIEW_CAPACITY_WAIT_MS` defaults to `45000`. It is a bounded admission budget separate from the monitor-specific Chromium execution deadline. The server caps admission plus execution at 110 seconds, below the reverse proxy's 120-second endpoint timeout and the frontend's 125-second request timeout. A 90-second monitor therefore has at most 20 seconds of admission waiting; a legacy fallback above 110 seconds remains unchanged for scheduled capture but is capped at 110 seconds for previews; a shorter monitor can use more of the configured admission budget. Waiting for a scheduled capture never reduces the browser's configured capture budget. While waiting, the API releases its PostgreSQL client between short advisory-lock probes and reports `capacity_wait` to the authenticated owner-bound status endpoint. Scheduled captures retain the priority gate. A cancelled HTTP request stops waiting immediately; a full local preview-waiter bound or elapsed budget returns a safe retryable capacity error without exposing database or browser details.

Region Preview now runs the same validated non-private Browser Steps sequence as a browser capture after navigation and before rendering/screenshot preparation. The preview request carries the monitor draft's `step_budget_ms`, and the existing per-step timeout, maximum 20 steps, CSS/XPath validation, origin checks, and `continue_on_error` rules apply unchanged. `fill_private` remains rejected for previews: no vault values, credentials, cookies, or private workflow data are sent to or read by the preview path.

The final main-frame HTTP response after Browser Steps is observed for both preview and scheduled capture. The preview presents a successful error-document capture as an origin-health warning rather than a healthy page. With error-page monitoring enabled, an initial HTTP error document skips unavailable Browser Steps; if a later step navigates to an error document, later unavailable required steps become the same safe warning. Authentication and challenge pages still fail closed. Element and selected-area error captures deliberately use the validated viewport fallback rather than recording a partial selector or crop result.

The Browser Steps editor can add a non-private step from the current Preview. It offers the visible element plus safe parent candidates and supports `click`, `wait_visible`, `wait_selector`, `dismiss_cookie`, and `scroll_to`. The step is appended only to the unsaved editor draft. **Replay preview** creates a fresh page with that draft workflow; a resident selection session is rejected if its URL, steps, budget, or browser controls no longer match the draft.

Selected element keeps one owner-bound 45-second session after its first preview. Point selection reuses that page and does not rerun Browser Steps. Selected area releases the browser, proxy, and admission lease once its preview PNG has returned; drawing and refresh state remain client-side. A new preview runs the latest saved draft Browser Steps again.


A preview request carries the unsaved Browser monitor `capture_timeout_ms` value. It accepts only 30, 45, 60, 75, or 90 seconds. Structured failures expose only the safe `preview_stage`, `failure_code`, duration, and request ID. Optional Browser Step failures remain warnings; required Browser Step failures retain their `browser_steps` stage and are never mislabeled as an element-selection ambiguity.

## Browser experience controls

Browser monitors can opt in to error-page monitoring. When enabled, an HTTP error document is captured as page content instead of being converted into a capture transport failure. The observed status is recorded as bounded numeric metadata; an error-page status transition is compared independently from pixels and text. DNS, TLS, SSRF, browser-launch, and challenge failures remain failures. The feature never attempts to bypass a WAF, CAPTCHA, or rate limit.

Status-only transitions are normal change events and are not filtered by text direction. Their notification fingerprint includes the before/after status, while normal mute, cooldown, digest, and delivery handling remain in force. Capture failures have explicit alert modes: **Off**, **First or persistent failure**, and **Every failure**. HTTP observations are not capture failures.

The editor also provides opt-in JavaScript disabling, a fixed hostname-bound tracker blocklist, reject-only cookie-banner handling, a deadline-bounded post-step wait, and an isolated mobile browser profile. Automatic cookie handling is limited to visible consent/cookie containers and exact reject/decline/deny controls; an explicit `dismiss_cookie` step takes precedence. These choices apply to scheduled captures and draft previews. They can change rendered output, so editing them follows the normal non-destructive baseline reset policy. Mobile previews use their real 390 × 844 coordinate space; Selected-area coordinates remain desktop-only and are rejected for a mobile profile rather than converted silently.
